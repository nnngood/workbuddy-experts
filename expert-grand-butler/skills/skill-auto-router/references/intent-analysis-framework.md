# 第一步：需求与成果形态解析框架

> 目的：在任何技能检索动作之前，先把"要交付什么"钉死。**形态判断错一步，后面全错。**
> 成品是一张 **任务解析卡（Task Card）**，它是第二步匹配引擎的唯一输入。

---

## 一、任务六问（逐条问自己，答案落进任务解析卡）

| # | 问题 | 要落到卡里的字段 | 判断要点 |
|---|---|---|---|
| 1 | **要什么？** | `task` | 保留用户原话，别急着改写成专业表述。原话里的名词往往就是最好的检索词。 |
| 2 | **给谁看？** | `audience`、`quality_bar` | 给领导呈报 / 给客户投标 / 给自己内部用 / 给公众传播 —— 质量线完全不同。 |
| 3 | **什么形态？** | `deliverable_forms` | **最容易被漏的一步**。见下方"形态识别陷阱"。 |
| 4 | **什么领域？** | `domain` | 水务、轨交、应急、医疗、电力、教育、金融、营销…… 领域词直接影响语义匹配。 |
| 5 | **有什么约束？** | `constraints` | 页数、字数、字号、色系、合规、必须含表格、必须不含某些信息、必须双版本。 |
| 6 | **什么标准算合格？** | `quality_bar` | 能看 / 能用 / 能呈报 / 能签署 / 能上会。 |

---

## 二、成果形态分类树（13 类标准形态）

匹配引擎用这 13 个标准键，**不要**自创新名字（新名字不会被识别）。

| 标准键 | 含义 | 典型信号词 |
|---|---|---|
| `word` | Word 正式文档 | 建议书、方案书、计划书、白皮书、标书、合同、公文、报告 |
| `ppt` | PPT 演示 | 汇报、路演、演示文稿、课件、幻灯片 |
| `excel` | 表格/工作簿 | 表格、台账、清单、预算表、测算表、统计表 |
| `html` | 网页/原型/看板 | 网页、网站、原型、看板、dashboard、交互页面 |
| `pdf` | PDF | 打印、印刷、画册、版式 |
| `chart` | 图表可视化 | 图表、折线、柱状、饼图、趋势、数据可视化 |
| `video` | 视频 | 视频、口播、短视频、分镜、配音、动画 |
| `image` | 图片 | 海报、封面、配图、插画、logo、抠图 |
| `code` | 代码/应用 | 脚本、程序、应用、接口、部署、重构 |
| `map` | 地图 | 地图、GIS、选址、路线 |
| `3d` | 3D 模型 | 三维、建模、glb、obj |
| `audio` | 音频 | 配音、语音合成、TTS、播客、响度 |
| `research` | 调研情报 | 调研、行业研究、竞品、尽调、情报 |

## 三、形态识别陷阱（**这一节是本文档的核心价值**）

### 陷阱 1：只说了名词，没说形态 → 必须追问或按默认推定

- "写一份 XX 方案" → 默认 `word`，但**要主动确认真的是否还要 `ppt`**。
- "给我讲讲 XX" → 不是任何交付物，是问答；**不要**启动技能路由。
- "做个 XX 的汇报" → 中文语境下"汇报"**通常同时意味着** `ppt` + 口播稿，可能还要 `word` 备用稿。

### 陷阱 2：隐含形态（话里没提，但场景必然需要）

| 用户说 | 隐含形态 | 依据 |
|---|---|---|
| 报给领导 / 上会 / 呈报 | `word` + `ppt` | 上会必有汇报材料 |
| 发抖音 / 视频号 / 公众号 | `video` 或 `word` + `image`（封面） | 平台内容需配封面 |
| 做数据分析 | `excel` + `chart` + 可能 `html` | 底稿、图表、报告三件套 |
| 投标 / 竞标 | `word`（正文）+ `ppt`（讲标）+ `excel`（报价） | 招投标标准三件 |

### 陷阱 3：只看结果形态，忽略**过程形态**

有些任务的主交付物是文档，但**真正的价值在过程产出**：澄清表、评分表、行动计划表（`excel`）、
风险清单、访谈提纲。这类"过程交付物"往往是客户最认的东西，必须在卡里显式写进 `deliverable_forms`。

### 陷阱 4：交付节奏（王老师固定偏好，务必遵守）

长篇正式文档默认走 **先 HTML 预览 → 再 Word 正式版**；正式方案默认 **Word + PPT 双版本**。
这是硬性约定，直接影响该不该把 `formal-doc-dual-delivery` 一类技能放进调用链。

## 四、任务解析卡（JSON 标准格式）

第二步的匹配引擎直接吃这个结构：

```json
{
  "task": "用户原话，原样保留",
  "task_type": "任务类型（用于组合库检索，见下方命名建议）",
  "deliverable_forms": ["word", "ppt"],
  "domain": "水务/智慧城市",
  "audience": "客户方决策层",
  "keywords": ["建议书", "报价", "水质监测", "机器人"],
  "constraints": ["正式可呈报", "含数据表格", "不得出现成本明细"],
  "quality_bar": "领导呈报级"
}
```

### `task_type` 命名建议（**决定组合记忆能不能命中**）

组合库以 `task_type` 为分类键，**同类任务必须用同一个名字**，否则记忆会碎片化。
建议只用下面这套固定词汇，不要每次另起新名：

```
正式方案类文档 | 投标竞标方案 | 战略规划咨询 | 行业研究报告 | 培训课程开发
简历筛选评价 | 短视频口播文案 | 企业站点建设 | 研讨会会议方案 | 商业计划书
数据定量分析 | 产品介绍视频 | 招标文件解读
```

> 若任务确属新类型，先按语义归入最接近的一项；只有当**第一次出现且明显不属任何现有类型**时，
> 才启用新名字，并在记录时保持后续一致。

## 五、自检清单（解析完卡，动手检索前过一遍）

- [ ] `task` 保留了用户原话？
- [ ] `deliverable_forms` 用的是 13 个标准键，没有自造词？
- [ ] 检查过"隐含形态"表，没漏掉汇报 PPT / 封面图 / 过程表单？
- [ ] `task_type` 用的是固定词汇表里的名字？
- [ ] 约束里写清了**不能出现什么**（比写"要什么"更容易被忽略）？
